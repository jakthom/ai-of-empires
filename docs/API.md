# API v1

Go serves the UI and `/api/v1` from the same origin. Requests carry intentions. The server determines movement, collisions, targets, resource changes, queues, damage, visibility, and results. The browser has no simulation loop; its animation loop interpolates observed positions and animates geometry.

[OpenAPI](../api/openapi.json) and [browser DTOs](../web/src/api.generated.ts) are generated by `go run ./cmd/contracts` from Go wire types registered in `internal/httpapi/contract.go`. Check drift with `go run ./cmd/contracts -check`. The contract is also served at `/api/v1/openapi.json`; the same-origin interactive [API reference](/api/docs) is powered by locally bundled Scalar.

## Multiplayer endpoints

The endpoint table and lifecycle diagrams are in [MULTIPLAYER.md](MULTIPLAYER.md#api). The complete generated contract is [OpenAPI](../api/openapi.json).

Create a saved private lobby with `POST /api/v1/games` and `Content-Type: application/json`:

```json
{
  "player_name": "Alice", "friends": 1,
  "config": {
    "name": "Evening kingdom", "settlements": 4,
    "civilization": "britons", "difficulty": "normal", "mode": "skirmish", "seed": 4817,
    "world": {"type": "islands", "biome": "tropical", "size": "medium", "treaty_minutes": 10}
  }
}
```

The `201 MemberSession` contains `match_id`, `membership_id`, `player_id`, `name`, `token`, `rejoin_code`, `epoch` and `owner`. Keep the rejoin code private. The server sets a host-local HttpOnly browser cookie and stores hashes of credentials. Game routes accept that browser's bound membership or `Authorization: Bearer <token>`; a bearer is resolved to its own player before simulation access. The browser cookie lists only its own games through `GET /games?q=…`. Names and IDs only search this authorized library.

`GET /games/{id}` returns lobby/roster/control metadata. `GET /games/{id}/snapshot` returns your world after Start. Commands, placement, log, entity history and SSE routes live beneath `/games/{id}`. Open a connection through `POST /games/{id}/connections`, then pass its ID as `?connection=…` to `/events`; it is a connection identifier, not a credential. Heartbeats and departures use `/connections/{connection}/heartbeat` and `/leave`.

Legacy `/matches` creation and authenticated single-player routes remain available for compatibility. They cannot authorize multiplayer games. Upgrade an old game with its original token through `POST /matches/{id}/adopt`. Unauthenticated `/sessions` listing and name-based recovery return 401; no game name grants a new token.

## World creation

`Catalog.worlds` is the source for world types, biomes, sizes (including tile counts), resource levels, starting separations, reveal modes, allowed treaty minutes, descriptions and defaults. `Config.world` is optional; omitted fields receive the catalog defaults. Unknown values return a structured 422 rule error. The seed is 1–999999999; omitted/zero defaults to 4817. `settlements` stays independent of size.

`Snapshot.world` and `SavedGame.world` contain the normalized creation settings. `Snapshot.map.biome` tells the renderer which scenery to use. `Snapshot.treaty_remaining` is the authoritative remaining time in game seconds. Do not run a client treaty clock or infer hostility from expiry. Attack and conversion commands during the initial peace period return `422 peace_period`; movement, economic work, and non-attacking attack-move travel remain available.

Go generates and validates terrain before publishing a session. Biomes do not affect rules. Natural resource abundance scales finite deposit amounts, not starting stockpiles, entity health, or farms. Hidden maps use normal visibility; explored maps expose terrain but retain entity fog; full reveal gives every kingdom full visibility. Terrain components route scouts, gathering and transport plans; they contain no foreign entity information. Older games retain their tiles and omit the new world type in their metadata (the UI labels them Original world).

## Durable sessions and shared controls

New games persist in Lobby without ticking. Configure seats, issue single-use invitations, claim them explicitly, and optionally mark Ready. The owner can start with unclaimed or unready human seats. Unclaimed kingdoms are created without AI, remain available to invite later, and do not trigger disconnect pauses. A first invitation or claim during play preserves the running clock. Start creates and checkpoints the finalized world before accepting gameplay commands. Human seats never run AI.

`POST /games/{id}/pause` and `/resume` take `{id, revision}`. Any member may pause; only the owner may resume or change speed. These are explicit intents, not toggles. The server rejects stale Resume revisions with `409 stale_revision`; use `Snapshot.control_revision` or `GameInfo.revision` from the observed state. Ready requests also check the last roster/rules revision, so peers can ready concurrently while a world change requires renewed approval.

Games autosave every 10 seconds, on explicit saves/leaves, and during graceful shutdown. No-human games pause and checkpoint before unloading. A human who connects and later disconnects pauses shared play after a 15-second grace; silent heartbeats expire after 12 seconds. Rejoin never resumes. Restart and import restore unfinished games paused without offline advancement. A crash can lose progress and receipts since the last committed checkpoint; acknowledged commands are not a durable input WAL.

Owner Close freezes and checkpoints before responding with `closed`. Failed writes remain `closing`, with Retry or Cancel available. Reopen returns a lobby or an unfinished paused world. Owner-confirmed Delete removes local saves, memberships, invitations and journals atomically, retaining a tombstone to reject stale autosaves. Exported files are unaffected. Move freezes the source before publishing its archive; import validates ownership and commits the restored game atomically. See the [portable game protocol](MULTIPLAYER.md#move-servers-or-play-on-a-lan).

The shared audit at `/games/{id}/audit?after=N` includes copied actor names, membership IDs and the `members` audience, with up to 200 records per page. Gameplay history remains independently filtered by each player's observations.

## Commands

```json
{
  "id": "a-client-generated-unique-id",
  "kind": "move",
  "entity_ids": [12, 13],
  "position": {"x": 25.5, "y": 41.5},
  "queue": false
}
```

Use actual entity IDs from the latest snapshot. Coordinates are map-space X/Y, not screen pixels. `position` is a requested destination/site; it does not assign authoritative coordinates.

| Kind | Additional fields |
|---|---|
| `move`, `attack_move` | `entity_ids`, `position`, optional `queue` |
| `interact`, `attack`, `gather`, `heal`, `convert`, `repair`, `relic`, `deposit_relic`, `garrison`, `trade` | `entity_ids`, `target_id`, optional `queue` |
| `build` | Villager `entity_ids`, building `product`, `position`, optional `queue` |
| `train`, `research` | One producer in `entity_ids`, catalog `product` |
| `age` | One Town Center in `entity_ids` |
| `cancel` | One producer in `entity_ids`, zero-based queue index in `value` |
| `rally` | One building in `entity_ids`, `position` |
| `deploy`, `unload` | One eligible entity in `entity_ids` |
| `stop`, `delete` | `entity_ids` |
| `stance` | `entity_ids`, `product`: `defensive` (default), `stand_ground`, `passive`, or `aggressive` |
| `reseed_farm` | One owned, depleted farm in `entity_ids`; pays 60 wood and assigns its farmer or the nearest idle villager on connected land |
| `market_buy`, `market_sell` | One market in `entity_ids`, `product`: `food`, `wood`, or `stone` |
| `resign` | No entity selection; resign only your own kingdom |
| `speed` (legacy adapter only; multiplayer uses `/speed`) | `value`: 1, 1.7, 3.4, 8, 16, or 32; supported values also come from `catalog.speeds` |

`interact` resolves the appropriate action on the server. To resume work on an existing foundation, use `interact` with its `target_id`; `build` creates a new site. Solid buildings cannot be placed on units. `pause` is a legacy single-player toggle; multiplayer uses explicit `/pause` and `/resume` controls. `deploy` toggles deployment/packing when its lifecycle permits it. Faster speeds run more fixed 50 ms simulation steps; they never increase the physics delta. Attainable wall-clock speed depends on server capacity.

`reseed_farm` fires the farm lifecycle from Exhausted to Foundation, charges once, and assigns construction through the villager lifecycle. Repeating it on the new foundation is refused. It reports `farm_not_depleted`, `insufficient_resources`, or `no_available_villager` when appropriate. Existing `interact` orders on depleted farms and automatic reseeding continue to use the same lifecycle.

For market exchange actions, optional `gain` has the same resource-object shape as `cost`. Render both from the snapshot; clients must not calculate exchange rates. The server validates and executes the same quote and appends an `exchange` event, included by the `economy` log filter. `trade` orders require an explored neutral Market and a completed owned Market on connected land.

Fishing uses `gather` or `interact` with a Fishing Ship and a Fish Shoal target. Fish have `resource: "food"`; cargo contributes to the Food stockpile only after delivery at a reachable Dock. Depletion removes the shoal through its lifecycle. Cargo, orders, remaining fish and reseeding progress are checkpointed normally.

`attack_move` optionally accepts `target_player`, the ID of another kingdom. It restricts proactive target acquisition to that kingdom; actual attackers from elsewhere can still provoke return fire. Omitted/zero means all other kingdoms, as an explicit offensive order. Other order kinds, one's own kingdom, and nonexistent IDs reject nonzero `target_player`. The server derives attack provenance and pursuit anchors; clients cannot supply them. `defensive` returns fire with limited pursuit, `stand_ground` returns fire without pursuit, `passive` suppresses automatic response, and `aggressive` enables unsolicited proximity attacks. Explicit attacks override automatic firing preferences.

A successful request returns `{command_id, tick, accepted: true}`. This acknowledges that the intention was accepted, not that a long-running order has completed. Completion arrives in snapshots.

Command IDs are required, 1–64 characters. Retrying the same decoded payload and ID returns the original result without applying it again. Reusing an ID with different content returns `409 idempotency_conflict`. Receipts are scoped to the authenticated membership. Both successful and rule-rejected commands are remembered for the game; use a new ID for a new attempt after conditions change. Use the same ID to resolve an ambiguous network failure. The UI does not automatically retry commands. Multiplayer limits are 60 new commands per member per second, 180 per game, 50,000 remembered commands per game, 64 queued unit orders, and 200 selected entities.

## Snapshots and reconnect

Snapshots contain simulation tick/time, match status, your economy, explored terrain/fog, observable entities and projectiles, and recent events. Entity views include a backend-derived `activity` label such as `Farming`, `Logging`, or `Mining stone`. Owned entity views contain current state, production progress, and server-computed actions with `enabled`, `reason`, `cost`, and `duration`. Render these fields; do not reproduce rules or infer affordability in the client. Actions can become stale between observation and command, so all commands are revalidated.

Owned entities also include `stance`; foreign stances remain private. Each `opponents` entry includes its relationship **with the authenticated player** (`relation`: `peaceful` or `hostile`) and a public `temperament` label (`Builder`, `Defensive`, `Expansionist`, or `Player controlled`). This does not disclose targets, army plans, or third-party relationships. Attacks and conversion attempts change relationships on the backend; quiet periods can restore peace. These fields and current stances survive checkpoint resume.

`Catalog.difficulties` supplies `{id, name, description}` for `peaceful`, `easy`, `normal`, `hard`, `extra_hard`, `expert`, and `aggressive`. Use these options when creating a match. `Snapshot.difficulty` supplies the current match's metadata, including after reconnect. Difficulty is fixed at creation. It changes Go's economic, production, research, and attack priorities; it does not grant extra starting resources or population.

Enemy units outside sight are omitted. Explored static objects can appear as last-known observations. Opponent economy and internal world state are not exposed. A snapshot read does not advance the simulation or RNG.

The stream sends `event: snapshot`, `id: <tick>`, and JSON `data` about every 100 ms. The Go simulation advances in fixed 50 ms steps, independently of rendering. The client uses streaming `fetch` to attach its bearer header. Reconnect sends a new complete current snapshot; `Last-Event-ID` is not a replay cursor. Replace prior presentation state and interpolate between observed positions without extrapolating game state.

## Immutable event history

Each match has a private append-only journal. Entries describe creation/discovery, accepted and rejected commands, committed lifecycle transitions, resource work and deliveries, production and cancellation, attacks and damage, healing, conversion, relics, and removal. Repeated simulation pulses are not individual log entries: continuous work is recorded at activity changes and meaningful outcomes. Event `id` is monotonically increasing across the match; `tick` and `time` are the authoritative simulation timestamp. Entity entries copy their ID, type, name, activity, state and position. Structured `kind`, `lifecycle`, `previous_state`, `target_id`, `resource`, `amount`, and `command_id` fields identify applicable details. Replaying an idempotent command adds no duplicate events.

Both history routes return `EventPage`. Events are always in ascending ID order. With no cursor, the newest 100 entries are returned. `limit` accepts 1–200. `after=N` returns events strictly after that ID (`after=0` starts at the beginning); `before=N` returns the nearest older page strictly before that ID. Cursors are mutually exclusive. The response includes `older_cursor`, `newer_cursor`, `latest_cursor`, `has_older`, and `has_newer`. IDs may have gaps due to fog filtering; never infer events by counting IDs. Entity history also includes `{id, name, type, activity, present}`. Unknown or never-observed entities return 404. A hidden entity's activity is explicitly last seen; its unobserved death is not revealed.

Both routes accept `q` (up to 200 characters) and `category`. Search is case-insensitive across the full retained authorized history, matching all words against messages, names, types, activities, resources, kinds, and states. Identity queries (an entity name followed by a number, an explicit `#ID`, or a lone number) match the exact actor ID: `q=Villager%203` or `q=%233` selects entity #3, never #30 or an unrelated entity merely mentioning #3. Numbers in ordinary searches such as `delivered 10 wood` match event text. Category IDs and labels come from `Catalog.log_filters`; the empty category means all. Example: `/log?q=villager%203&category=economy&limit=100`. Unknown categories, duplicate parameters, and oversized queries return 400.

Filters combine with entity scope and both cursor directions. Pagination flags and `latest_cursor` refer to matching events; an empty result retains an entity's current status and returns an empty event array. Keep filters unchanged while paging. Derived search indexes process new entries incrementally and cannot change history. Locate is a presentation action: use a currently observable entity position, or the selected event's recorded position when it is no longer visible. It needs no gameplay command.

Snapshots include at most 40 recent events and `event_cursor`, the latest authorized event ID. Use `/log?after=<last_consumed_id>` to catch up, following `has_newer` until caught up. The SSE snapshot tail is a preview, not complete history. History reads are observational and cannot advance the simulation. Visibility is captured when each event occurs, so exploring an enemy later never reveals its earlier hidden orders. Histories survive entity removal, browser closure, unloading, and server restarts. New records append to SQLite at each checkpoint; individual records are never rewritten. Permanently deleting a game also deletes its history. There are no endpoints to edit or delete individual entries.

## Placement and errors

`POST /placement` accepts `{"product":"house","position":{"x":24.5,"y":40.5}}` and returns `{valid, reason?}`. Preview validity is advisory: the building command validates the site again and commits payment and construction on the server.

Errors have the shape `{"error":{"code":"paused","message":"Resume the match before issuing an order."}}`. HTTP statuses distinguish malformed JSON/unknown fields (`400`), missing/invalid authentication (`401`), cross-origin refusal (`403`), missing/expired matches (`404`), command ID conflicts (`409`), unsupported content type (`415`), gameplay refusal (`422`), rate limits (`429`), and capacity or shutdown (`503`). Ordinary JSON bodies are limited to 16 KiB. Archive imports use multipart uploads with a 64 MB file limit. Clients cannot supply fields such as HP, damage, owner, or resources.

This server supports up to 16 loaded games with up to six human/AI kingdoms each; additional saves remain in SQLite. Reconnect receives a fresh authorized view. Public matchmaking, replay playback and external account services remain future extensions.
